# Architecture Decision Records

## 철학

Crate Finder는 작동하는 MVP를 빠르게 만들되, 이후 실제 서비스화가 가능한 구조를 유지한다.

핵심 가치관은 다음과 같다.

- 사용자 경험 우선: DJ가 보유곡/누락곡을 빠르게 판단할 수 있어야 한다.
- 데이터 흐름 명확성: 유튜브 데이터, Rekordbox XML 데이터, 매칭 결과의 흐름을 분리한다.
- 보안 기본값 우선: 원본 XML은 기본적으로 저장하지 않는다.
- 테스트 가능한 핵심 로직: parser, normalizer, matcher는 UI와 분리한다.
- 외부 의존성 격리: 유튜브 API, 가격 Provider, DB는 서비스 계층으로 분리한다.
- 디자인은 컴포넌트 계층에 제한: 레트로 UI가 도메인 로직을 오염시키지 않는다.
- Claude Code 작업 안정성: 작은 phase/step 단위로 구현하고 PR 리뷰 후 merge한다.

---

## ADR-001: Next.js App Router 선택

**결정**: Next.js App Router를 기본 웹 프레임워크로 사용한다.

**이유**:
- 페이지와 API Route를 하나의 프로젝트에서 관리할 수 있다.
- Server Component를 활용해 서버 데이터 조회와 UI 렌더링을 분리할 수 있다.
- 유튜브 API, XML 파싱, 가격 Provider 같은 서버 로직을 같은 코드베이스에서 관리하기 쉽다.
- MVP 단계에서 별도 백엔드 서버를 두지 않아도 된다.

**트레이드오프**:
- API가 복잡해질 경우 별도 백엔드 분리가 필요할 수 있다.
- 파일 업로드와 대용량 XML 파싱은 서버리스 환경 제약을 받을 수 있다.
- App Router 패턴을 잘못 사용하면 Server/Client Component 경계가 흐려질 수 있다.

## ADR-002: TypeScript strict mode 사용

**결정**: TypeScript strict mode를 사용한다.

**이유**:
- YouTubeTrack, RekordboxTrack, MatchResult 등 도메인 타입이 명확해야 한다.
- 매칭 로직에서 `undefined`, 누락 필드, 불완전 메타데이터를 안전하게 처리해야 한다.
- Claude Code가 코드를 생성할 때 타입 오류를 조기에 발견할 수 있다.
- parser와 matcher 테스트 안정성이 높아진다.

**트레이드오프**:
- 초기 개발 속도가 약간 느려질 수 있다.
- 외부 API 응답이나 XML 파싱 결과에는 타입 보정 코드가 필요하다.

---

## ADR-003: 외부 API 호출은 서버에서만 수행

**결정**: 유튜브 API, 가격 조회 API, 외부 Provider 호출은 클라이언트에서 직접 수행하지 않는다. 모든 외부 호출은 API Route 또는 service 계층에서 수행한다.

**이유**:
- API Key가 클라이언트 번들에 노출되면 안 된다.
- 외부 API 오류를 서버에서 표준화된 오류 코드로 변환할 수 있다.
- 쿼터 제한, 캐시, 재시도 정책을 서버에서 통제할 수 있다.
- 가격 Provider가 바뀌어도 UI 변경을 최소화할 수 있다.

**트레이드오프**:
- API Route 설계와 서버 검증 코드가 필요하다.
- 클라이언트에서 직접 호출하는 것보다 구현 단계가 하나 늘어난다.

## ADR-004: 원본 Rekordbox XML 기본 미저장

**결정**: MVP 기본 정책은 원본 Rekordbox XML 파일을 저장하지 않는 것이다. 서버에서 파싱 후 필요한 메타데이터만 추출하고 원본은 폐기한다.

**이유**:
- XML에는 로컬 파일 경로, 라이브러리 구조 등 개인 작업 환경 정보가 포함될 수 있다.
- 원본 파일 저장은 보안, 개인정보, 저장소 관리 리스크를 키운다.
- 이 서비스의 핵심 기능은 원본 파일 보관이 아니라 트랙 비교와 분석이다.
- 사용자 신뢰 확보를 위해 “Original XML is parsed and discarded” 정책을 UI에 명시한다.

**트레이드오프**:
- 동일 XML로 완전한 재분석을 하려면 사용자가 다시 업로드해야 할 수 있다.
- 디버깅 시 원본 샘플 확보가 어렵다.
- 향후 사용자가 원본 보관을 원할 경우 암호화 저장 옵션을 별도 설계해야 한다.

## ADR-005: XML 파싱 로직은 UI와 분리

**결정**: Rekordbox XML 파싱은 `lib/rekordbox`에 두고 UI 컴포넌트에서는 직접 XML 구조를 다루지 않는다.

**이유**:
- 파싱 로직은 테스트가 중요하다.
- Rekordbox XML 형식 변경에 대응하려면 파서만 수정할 수 있어야 한다.
- UI에서 XML DOM을 직접 다루면 유지보수성이 떨어진다.
- 파일 검증, 파싱, 필드 매핑, 경고 처리를 단계별로 분리할 수 있다.

**트레이드오프**:
- 초기에는 파일 수가 늘어난다.
- 간단한 파싱도 별도 함수로 나눠야 하므로 작성량이 증가한다.

---

## ADR-006: 트랙 정규화/매칭 로직은 순수 함수 중심으로 구현

**결정**: 제목/아티스트 정규화, 정확 일치 매칭, 유사도 매칭, 신뢰도 산정은 `lib/matching`의 순수 함수로 구현한다.

**이유**:
- 이 서비스의 핵심 품질은 매칭 정확도다.
- 순수 함수는 테스트가 쉽고 회귀 버그를 줄일 수 있다.
- UI와 분리하면 디자인 변경이 매칭 로직에 영향을 주지 않는다.
- 다양한 표기 흔들림을 테스트 케이스로 축적할 수 있다.

**트레이드오프**:
- 고급 매칭을 위해 별도 알고리즘 또는 라이브러리가 필요할 수 있다.
- 정규화 규칙이 과하면 오매칭이 발생할 수 있어 기준 조정이 필요하다.

---

## ADR-007: 매칭 결과는 `owned`, `missing`, `needs_review`로 표준화

**결정**: 매칭 상태값은 `owned`, `missing`, `needs_review` 세 가지로 표준화한다.

**이유**:
- 사용자가 실제로 판단해야 하는 상태가 명확해진다.
- `needs_review`를 두면 애매한 후보를 잘못된 보유/누락으로 확정하지 않아도 된다.
- UI 배지, 필터, 분석 요약 지표를 일관되게 구성할 수 있다.
- 수동 매칭 확정 플로우와 자연스럽게 연결된다.

**트레이드오프**:
- 단순한 보유/누락 이분법보다 UI가 약간 복잡해진다.
- 사용자가 확인해야 하는 항목이 생기므로 추가 인터랙션이 필요하다.

---

## ADR-008: 매칭 신뢰도는 `high`, `medium`, `low`로 표시

**결정**: 매칭 결과에는 신뢰도 값을 함께 제공한다. 신뢰도는 `high`, `medium`, `low`로 표시한다.

**이유**:
- 트랙 제목과 아티스트 표기는 다양한 변형이 존재한다.
- 신뢰도를 표시하면 사용자가 결과를 맹신하지 않고 검토할 수 있다.
- 낮은 신뢰도 항목만 필터링하여 수동 확인할 수 있다.
- 향후 매칭 알고리즘 개선 기준으로 활용할 수 있다.

**트레이드오프**:
- 신뢰도 산정 기준을 지속적으로 조정해야 한다.
- 잘못 설계하면 사용자가 신뢰도 기준을 이해하기 어렵다.

---

## ADR-009: 가격 조회는 Provider 패턴으로 분리

**결정**: 가격 조회 및 구매 링크 제공은 `PriceProvider` 인터페이스로 분리한다. MVP에서는 Mock Provider와 Search Link Provider를 우선 사용한다.

**이유**:
- 음악 판매 사이트는 API 정책, 크롤링 허용 여부, 가격 표시 방식이 다르다.
- 처음부터 실시간 최저가를 완성하려 하면 MVP 일정이 지연된다.
- Provider 패턴을 사용하면 사이트별 구현을 독립적으로 추가할 수 있다.
- 가격 조회 실패 시 검색 링크 fallback을 제공할 수 있다.

**트레이드오프**:
- MVP의 가격 정보는 실제 최저가가 아닐 수 있다.
- 사용자가 기대하는 “최저가 자동 비교”와 초기 구현 사이에 간극이 생길 수 있다.
- 각 Provider별 유지보수 비용이 발생한다.

## ADR-010: 디자인은 Classic Macintosh-inspired DJ Workstation으로 적용

**결정**: UI 디자인은 `Classic Macintosh-inspired DJ Workstation` 방향을 따른다.

**이유**:
- DJ crate, 라이브러리, 파일 탐색, 매칭 결과 테이블이라는 제품 특성과 레트로 데스크톱 감성이 잘 맞는다.
- 레트로 Macintosh 감성은 Finder, 파일 관리, 작업용 프로그램의 이미지를 제공한다.
- 일반적인 AI SaaS 디자인과 차별화할 수 있다.
- 결과 테이블 중심 UI와 클래식 데스크톱 창 패널 구조가 잘 맞는다.

**트레이드오프**:
- 과하게 적용하면 장난감 같은 UI가 될 수 있다.
- 픽셀 폰트, 과도한 장식, 낮은 대비는 가독성을 해칠 수 있다.
- 실제 Apple 로고, 아이콘, OS UI를 복제하지 않도록 주의해야 한다.

## ADR-011: 전역 상태 관리 라이브러리는 MVP에서 도입하지 않음

**결정**: MVP에서는 Redux, Zustand 등 전역 상태 관리 라이브러리를 기본 도입하지 않는다.

**이유**:
- 초기 상태 대부분은 입력폼, 업로드 상태, 필터, 정렬 같은 로컬 UI 상태다.
- 분석 결과와 분석 내역은 서버 상태로 관리할 수 있다.
- 불필요한 상태 관리 계층을 추가하면 Claude Code 작업 복잡도가 높아진다.
- 필요성이 명확해진 뒤 도입하는 것이 낫다.

**트레이드오프**:
- 페이지 간 복잡한 상태 공유가 필요해지면 리팩토링이 필요할 수 있다.
- 수동 매칭, 분석 진행 상태, 대량 결과 캐시가 커지면 별도 상태 관리 도구가 필요할 수 있다.

---

## ADR-012: 데이터베이스는 PostgreSQL 계열을 기준으로 설계

**결정**: 데이터 저장소는 PostgreSQL 또는 Supabase Postgres를 기준으로 설계한다. ORM은 Prisma를 사용한다.

**이유**:
- 분석 세션, 트랙 스냅샷, 매칭 결과, 수동 매칭 규칙, 클릭 이벤트를 관계형으로 관리하기 적합하다.
- Prisma를 사용하면 TypeScript 타입과 DB 모델을 연결하기 쉽다.
- Supabase를 사용할 경우 인증, DB, 스토리지 확장 가능성이 있다.
- MVP 이후 서비스화에 적합한 선택이다.

**트레이드오프**:
- 단순 로컬 MVP보다 초기 설정이 늘어난다.
- 마이그레이션 관리가 필요하다.
- 원본 XML을 저장하지 않는 정책과 별도로 메타데이터 저장 범위를 신중히 설계해야 한다.

## ADR-013: 파일 업로드는 서버 API Route에서 처리

**결정**: Rekordbox XML 파일 업로드와 파싱은 서버 API Route를 통해 처리한다.

**이유**:
- 원본 XML을 클라이언트에서 오래 들고 있지 않아도 된다.
- 서버에서 파일 크기, MIME, 확장자, XML 구조 검증을 일관되게 처리할 수 있다.
- XML 원본 로그 금지, 민감정보 마스킹 등 보안 처리를 서버에서 통제할 수 있다.
- 파싱 실패 시 표준 오류 코드로 변환할 수 있다.

**트레이드오프**:
- 서버리스 환경에서는 파일 크기와 실행 시간 제한을 고려해야 한다.
- 매우 큰 XML 처리에는 별도 업로드/처리 인프라가 필요할 수 있다.

---

## ADR-014: Claude Code 작업은 PR 기반으로만 반영

**결정**: Claude Code가 생성한 코드는 직접 main에 반영하지 않고, 작업 브랜치에서 PR을 생성한 뒤 사람이 확인하고 merge한다.

**이유**:
- Claude가 의도보다 넓은 범위를 수정할 수 있다.
- 기능 구현, 리팩토링, 디자인 변경이 섞이는 것을 방지해야 한다.
- 사람이 요구사항 적합성, UI, 보안, 테스트 결과를 검토해야 한다.
- main branch 안정성을 유지할 수 있다.

**트레이드오프**:
- 개발 속도는 직접 push보다 느리다.
- PR 관리와 리뷰 시간이 필요하다.
- GitHub branch protection, CI, PR template 설정이 필요하다.

## ADR-015: Conventional Commits 사용

**결정**: 커밋 메시지는 Conventional Commits 형식을 사용한다.

**이유**:
- Claude Code가 변경 목적을 일관되게 기록할 수 있다.
- PR 리뷰 시 변경 성격을 빠르게 파악할 수 있다.
- changelog, release note 자동화로 확장 가능하다.
- 기능, 버그, 문서, 테스트, 리팩토링을 구분하기 쉽다.

**형식**:

```txt
type(scope): summary
```

**허용 타입**:

```txt
feat, fix, docs, style, refactor, test, chore, perf, ci, build
```

**예시**:

```txt
feat(youtube): add playlist url parser
fix(rekordbox): handle xml encoding errors
docs(ui): add macintosh-inspired ui guide
test(matching): add normalization test cases
```

**트레이드오프**:
- 커밋 메시지 작성 규칙을 지켜야 한다.
- 작은 작업에도 scope를 고민해야 할 수 있다.

## ADR-016: 테스트 우선순위는 parser, normalizer, matcher

**결정**: MVP 테스트의 최우선 대상은 parser, normalizer, matcher로 한다.

**이유**:
- 이 서비스의 정확도는 XML 파싱과 트랙 매칭 품질에 달려 있다.
- UI보다 도메인 로직의 회귀 방지가 중요하다.
- 다양한 제목 표기와 XML 변형을 테스트 케이스로 관리해야 한다.
- Claude Code가 로직을 수정할 때 기존 동작을 깨는 것을 방지할 수 있다.

**트레이드오프**:
- 초기 UI 구현보다 테스트 작성 시간이 늘어난다.
- 테스트 데이터 관리가 필요하다.
- 실제 사용 데이터가 쌓이면 테스트 케이스를 계속 보강해야 한다.

---

## ADR-017: MVP에서는 검색 링크 기반 구매 액션을 우선 제공

**결정**: MVP에서는 실시간 가격 API보다 사이트별 검색 링크 기반 구매 액션을 우선 제공한다.

**이유**:
- 음악 판매 사이트별 API 제공 여부와 정책이 불확실하다.
- 크롤링 기반 최저가 비교는 법적/운영 리스크가 있다.
- 검색 링크만으로도 사용자는 누락곡 구매 탐색 시간을 줄일 수 있다.
- Provider 구조를 먼저 만들면 후속 실제 연동으로 확장 가능하다.

**트레이드오프**:
- MVP에서 “최저가 자동 비교” 경험은 제한적이다.
- 사용자가 외부 사이트에서 다시 확인해야 한다.
- 가격 정확성 KPI는 후속 단계에서 측정해야 한다.

## ADR-018: 모바일보다 데스크톱/태블릿 우선

**결정**: MVP UI는 데스크톱/태블릿 사용성을 우선한다.

**이유**:
- DJ가 Rekordbox XML을 내보내고 업로드하는 작업은 주로 데스크톱 환경에서 발생한다.
- 분석 결과 테이블은 넓은 화면에서 더 효과적이다.
- 파일 업로드, 필터링, 수동 매칭은 모바일보다 데스크톱에 적합하다.
- 레트로 데스크톱 디자인 컨셉과도 맞다.

**트레이드오프**:
- 모바일 완성도는 후순위가 된다.
- 모바일에서는 테이블을 카드형으로 전환하는 별도 처리가 필요하다.
