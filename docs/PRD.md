# PRD: Crate Finder

## 1. 제품 개요

### 1.1 프로젝트명

- Repository: `crate-finder`
- Product Name: `Crate Finder`
- Internal Description: 레코드박스 연동 DJ 음악 관리 툴

### 1.2 한 줄 정의

유튜브 플레이리스트와 Rekordbox XML 라이브러리를 비교하여 보유곡, 누락곡, 확인 필요 곡을 식별하고, 누락곡에 대한 구매 액션을 제공하는 DJ 음악 라이브러리 관리 웹앱.

### 1.3 제품 목표

전문 DJ가 유튜브에서 발견한 플레이리스트를 실제 DJ 셋 준비 과정에 빠르게 반영할 수 있도록, 유튜브 플레이리스트와 Rekordbox 라이브러리를 자동 비교하고 누락곡 확인 및 구매 탐색 과정을 단축한다.

### 1.4 해결하려는 문제

DJ는 새로운 음악을 유튜브 플레이리스트로 탐색하는 경우가 많지만, 해당 곡이 자신의 Rekordbox 라이브러리에 이미 있는지 확인하려면 수동 검색이 필요하다. 이 과정에서 다음 문제가 발생한다.

- 플레이리스트 곡을 하나씩 Rekordbox에서 검색해야 하는 비효율
- 이미 보유한 곡을 중복 구매할 가능성
- 누락곡을 어디서 구매해야 하는지 다시 검색해야 하는 번거로움
- 제목, 아티스트, Remix, Edit, feat. 표기 차이로 인한 매칭 오류
- XML 파일, 플레이리스트, 분석 결과를 반복적으로 관리하기 어려움

### 1.5 핵심 가치

- 수동 검색 시간을 줄인다.
- 보유곡/누락곡 판단을 빠르게 한다.
- 매칭 신뢰도를 표시하여 잘못된 판단을 줄인다.
- 누락곡에 대한 다음 행동을 바로 제공한다.
- 원본 XML 파일 저장을 최소화하여 사용자 데이터 노출 위험을 줄인다.

## 2. 사용자

### 2.1 주요 사용자

| 사용자 | 설명 |
|---|---|
| 전문 DJ | 정기적으로 새로운 음악을 탐색하고 Rekordbox 기반으로 셋을 준비하는 사용자 |
| 클럽 DJ | 공연 전 플레이리스트와 보유 라이브러리를 빠르게 비교해야 하는 사용자 |
| 라디오 DJ | 방송용 선곡 목록과 보유 음원을 관리하는 사용자 |
| 음악 라이브러리 관리자 | 대량의 트랙을 정리하고 중복/누락 여부를 확인하는 사용자 |

### 2.2 사용자 시나리오

DJ 준은 매주 유튜브에서 새로운 트랙을 탐색하여 플레이리스트를 만든다. Crate Finder에 접속하여 유튜브 플레이리스트 URL을 입력하고, Rekordbox에서 내보낸 XML 파일을 업로드한다. 시스템은 플레이리스트의 트랙을 분석하고, Rekordbox 라이브러리에 이미 존재하는 곡과 누락된 곡을 구분한다. 준은 누락곡만 필터링하여 확인하고, 구매 가능한 사이트 링크를 통해 필요한 곡을 구매한다.

## 3. 사용자 플로우

```txt

→ 플레이리스트 곡 목록 불러오기

→ XML 파일 검증

→ 트랙 정규화
→ 보유/누락/확인필요 매칭
→ 분석 결과 표시
→ 누락곡 구매 액션
→ 분석 내역 저장/재실행
→ 데이터 삭제/설정 관리
```

### 3.2 MVP 핵심 플로우

```txt
유튜브 URL 입력
→ Rekordbox XML 업로드
→ 분석 실행

→ 누락만 보기
→ 구매 검색 링크 이동
```

## 4. MVP 범위

### 4.1 MVP 포함 기능

#### 1. 유튜브 플레이리스트 연동

- 사용자가 유튜브 플레이리스트 URL을 입력한다.
- URL 형식을 검증한다.
- `playlistId`를 추출한다.
- 유튜브 플레이리스트 항목을 불러온다.
- 영상 제목, 채널명, 게시 정보 등 기본 정보를 수집한다.
- 영상 제목에서 아티스트/곡명을 추정한다.
- 삭제/비공개/중복 영상은 별도 상태로 처리한다.

#### 2. Rekordbox XML 업로드 및 파싱

- 사용자가 Rekordbox에서 내보낸 XML 파일을 업로드한다.
- 확장자, 파일 크기, XML 유효성을 검사한다.
- XML에서 트랙 메타데이터를 추출한다.
- 제목, 아티스트, 앨범, 길이, 위치 등 기본 필드를 내부 모델로 매핑한다.
- 인코딩/특수문자 문제를 완화한다.
- 원본 XML은 기본적으로 저장하지 않고 파싱 후 폐기한다.

#### 3. 트랙 정규화 및 매칭

- 제목/아티스트 문자열을 정규화한다.
- 대소문자, 공백, 특수문자, 괄호 표기, feat. 표기 등을 비교 가능한 형태로 정리한다.
- 1차 정확 일치 매칭을 수행한다.
- 2차 유사도 기반 후보 매칭을 수행한다.
- 매칭 결과를 `보유`, `누락`, `확인 필요`로 구분한다.
- 매칭 신뢰도를 `높음`, `보통`, `낮음`으로 표시한다.
- 신뢰도가 낮은 항목은 수동 후보 확인 대상으로 표시한다.

#### 4. 분석 결과 UI

- 매칭 결과 목록을 테이블로 표시한다.
- 보유/누락/확인필요 상태를 배지로 표시한다.
- 누락만 보기, 보유만 보기, 신뢰도 낮음만 보기 필터를 제공한다.
- 긴 트랙명과 아티스트명은 가독성을 유지하면서 표시한다.
- 분석 요약 정보를 표시한다.
  - 전체 트랙 수
  - 보유 곡 수
  - 누락 곡 수
  - 확인 필요 곡 수

#### 5. 누락곡 구매 액션

- 누락곡에 대해 구매하기 액션을 제공한다.
- MVP에서는 실제 가격 API 연동보다 사이트별 검색 링크 또는 Mock Price Provider를 우선 적용한다.
- 구매 링크는 새 탭으로 연다.
- 구매 링크 클릭 이벤트를 추적할 수 있는 구조를 마련한다.

#### 6. 분석 내역 저장 및 재실행

- 최근 분석 내역을 목록으로 표시한다.
- 분석 내역에는 플레이리스트 URL, 분석 시각, 전체 곡 수, 누락 곡 수를 포함한다.
- 같은 조건으로 다시 분석할 수 있는 진입점을 제공한다.
- MVP에서는 원본 XML이 아닌 파싱된 최소 메타데이터와 분석 결과 중심으로 저장한다.

#### 7. 오류 처리 및 가이드

- 유효하지 않은 유튜브 URL 오류를 안내한다.
- 비공개/삭제된 플레이리스트 오류를 안내한다.
- API 제한 또는 네트워크 오류를 안내한다.
- XML 파일 형식 오류를 안내한다.
- XML 필수 필드 누락, 인코딩, 파싱 실패를 구분한다.
- 각 오류에는 재시도 버튼과 해결 가이드를 포함한다.

#### 8. 개인정보/보안 및 파일 관리

- 업로드한 XML 원본 저장 여부를 명확히 안내한다.
- 기본 정책은 원본 XML 미저장이다.
- 사용자가 분석 내역을 삭제할 수 있게 한다.
- 사용자가 업로드/분석 데이터를 삭제할 수 있게 한다.
- 개인정보 처리방침 또는 데이터 보관 정책 진입점을 제공한다.

## 6. 기능 요구사항

### 6.1 유튜브 플레이리스트 URL 입력

#### 요구사항

- 사용자는 유튜브 플레이리스트 URL을 입력할 수 있어야 한다.
- 시스템은 URL이 지원 가능한 형식인지 검증해야 한다.
- 시스템은 URL에서 `playlistId`를 추출해야 한다.
- 오류 발생 시 원인과 해결 방법을 표시해야 한다.

#### 수용 기준

- 유효한 playlist URL 입력 시 다음 단계로 진행된다.
- 유효하지 않은 URL 입력 시 오류 메시지가 표시된다.
- `playlistId`가 없는 URL은 분석을 진행하지 않는다.

### 6.2 플레이리스트 곡 목록 불러오기

#### 요구사항

- 시스템은 유튜브 API를 통해 플레이리스트 항목을 불러와야 한다.
- 페이지네이션을 지원해야 한다.
- 삭제/비공개 영상은 별도 상태로 표시하거나 제외해야 한다.
- 중복 영상 처리 정책을 적용해야 한다.

#### 수용 기준

- 플레이리스트 내 영상 목록이 화면에 표시된다.
- 항목 수가 많은 플레이리스트도 전체 수집이 가능하다.
- 삭제/비공개 영상은 사용자가 이해할 수 있는 상태로 표시된다.

### 6.3 트랙 정보 추출

#### 요구사항

- 영상 제목에서 아티스트와 곡명을 추정해야 한다.
- 일반적인 표기 패턴을 인식해야 한다.
  - `Artist - Title`
  - `Artist – Title`
  - `Artist - Title (Remix)`
  - `Artist feat. Artist - Title`
- 추출이 불확실한 항목은 확인 필요 상태로 표시해야 한다.

#### 수용 기준

- 일반적인 `Artist - Title` 형식은 정상 파싱된다.
- 불확실한 제목은 임의 확정하지 않고 확인 필요로 분류된다.

### 6.4 Rekordbox XML 업로드

#### 요구사항

- 사용자는 XML 파일을 업로드할 수 있어야 한다.
- 시스템은 파일 확장자, 크기, XML 구조를 검증해야 한다.
- 업로드 및 파싱 진행 상태를 표시해야 한다.
- 실패 시 재업로드할 수 있어야 한다.

#### 수용 기준

- `.xml` 파일만 허용된다.
- 잘못된 파일은 파싱하지 않고 오류를 표시한다.
- 업로드 성공 후 파싱 결과 요약을 표시한다.

### 6.5 Rekordbox XML 파싱

#### 요구사항

- XML에서 트랙 목록을 생성해야 한다.
- 제목, 아티스트, 앨범, 길이 등 주요 필드를 내부 모델로 매핑해야 한다.
- 인코딩 및 특수문자 문제를 완화해야 한다.
- 원본 XML 파일 내용은 로그에 남기지 않는다.

#### 수용 기준

- XML 내 트랙 수와 파싱된 트랙 수가 표시된다.
- 필수 필드가 없는 항목은 오류가 아니라 경고 또는 불완전 데이터로 처리한다.
- 파서 로직은 UI와 분리되어 테스트 가능해야 한다.

### 6.6 트랙 매칭

#### 요구사항

- 유튜브 트랙과 Rekordbox 트랙을 비교해야 한다.
- 정규화된 제목+아티스트 정확 일치를 우선 적용해야 한다.
- 정확 일치가 없으면 유사도 기반 후보를 생성해야 한다.
- 매칭 신뢰도를 산정해야 한다.
- 수동 매칭 확정이 가능해야 한다.

#### 수용 기준

- 정확 일치 항목은 `보유`로 표시된다.
- 매칭 후보가 애매한 항목은 `확인 필요`로 표시된다.
- 후보가 없는 항목은 `누락`으로 표시된다.
- 수동 확정 결과는 이후 분석에서 우선 재사용할 수 있는 구조여야 한다.

### 6.7 결과 필터/정렬

#### 요구사항

- 누락만 보기
- 보유만 보기
- 확인 필요만 보기
- 신뢰도 낮음만 보기
- 가격 낮은 순 또는 추천 액션 정렬은 가격 Provider 적용 후 확장

#### 수용 기준

- 필터 클릭 시 테이블 항목이 즉시 갱신된다.
- 필터 상태가 UI에 명확히 표시된다.
- 필터는 다른 상태와 충돌하지 않는다.

### 6.8 구매 액션

#### 요구사항

- 누락곡에 대해 구매 링크 또는 검색 링크를 제공해야 한다.
- 여러 판매 사이트가 있을 경우 최저가 또는 추천 링크를 강조할 수 있어야 한다.
- 외부 링크는 새 탭에서 열린다.
- 링크 클릭 이벤트를 기록할 수 있어야 한다.

#### 수용 기준

- 누락곡 상세 또는 결과 행에서 구매 액션을 확인할 수 있다.
- 가격 정보가 없는 경우에도 사이트별 검색 링크를 제공한다.
- 링크 오류 시 대체 안내를 표시한다.

### 6.9 분석 내역

#### 요구사항

- 사용자는 최근 분석 내역을 볼 수 있어야 한다.
- 분석 내역에서 다시 분석을 실행할 수 있어야 한다.
- 분석 시각, 곡 수, 누락 수를 표시해야 한다.

#### 수용 기준

- 분석 완료 후 대시보드에 내역이 추가된다.
- 다시 분석 버튼을 통해 동일 플레이리스트 기준 분석을 재실행할 수 있다.
- 저장 데이터는 최소화한다.

### 6.10 데이터 삭제

#### 요구사항

- 사용자는 분석 내역을 삭제할 수 있어야 한다.
- 사용자는 파싱된 라이브러리 데이터 또는 전체 데이터를 삭제할 수 있어야 한다.
- 삭제 전 확인 절차를 제공해야 한다.

#### 수용 기준

- 삭제 후 해당 분석 내역이 목록에서 사라진다.
- 삭제 액션은 되돌릴 수 없음이 명확히 안내된다.
- 원본 XML 저장 정책을 설정 화면에서 확인할 수 있다.

## 7. 비기능 요구사항

### 7.1 보안

- API Key는 클라이언트에 노출하지 않는다.
- 유튜브 API 및 가격 조회는 서버 라우트 또는 서비스 계층에서 처리한다.
- 원본 XML 내용은 로그에 출력하지 않는다.
- 원본 XML은 기본적으로 저장하지 않는다.
- 사용자가 삭제를 요청하면 분석 데이터와 파싱 메타데이터를 삭제한다.

### 7.2 성능

- XML 파싱은 UI 스레드를 장시간 막지 않도록 설계한다.
- 대량 트랙 목록 표시 시 가상 스크롤 도입을 검토한다.
- 필터/정렬은 불필요한 전체 리렌더링을 줄인다.
- 외부 API 응답은 적절히 캐시하되, 가격 정보는 TTL을 명확히 둔다.
- 검색 입력에는 debounce를 적용한다.

### 7.3 안정성

- 외부 API 실패를 전체 앱 장애로 전파하지 않는다.
- 유튜브 API, 가격 Provider, XML 파서는 독립적으로 실패 처리한다.
- 실패 시 재시도 버튼과 원인 메시지를 제공한다.
- 파싱 실패 항목이 일부 있어도 전체 분석은 가능한 범위에서 진행한다.

### 7.4 접근성

- 버튼, 입력창, 테이블은 semantic HTML을 사용한다.
- 상태값은 색상만으로 표현하지 않는다.
- 키보드 포커스 상태를 제거하지 않는다.
- 테이블 헤더에는 적절한 `th`와 `scope`를 사용한다.

## 13. MVP 완료 기준

MVP는 다음 조건을 만족하면 완료로 본다.

- 사용자가 유튜브 플레이리스트 URL을 입력할 수 있다.
- 사용자가 Rekordbox XML 파일을 업로드할 수 있다.
- 시스템이 두 데이터셋을 내부 Track 모델로 변환한다.
- 시스템이 보유/누락/확인필요 상태를 표시한다.
- 사용자가 누락곡만 필터링할 수 있다.
- 누락곡에 대해 구매 검색 링크를 열 수 있다.
- 주요 오류에 대해 재시도와 안내가 제공된다.
- 원본 XML 저장 정책이 명확히 표시된다.
- 핵심 로직에는 단위 테스트가 존재한다.
